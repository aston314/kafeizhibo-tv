# 电视端请求超时与连接恢复

核验日期：2026-10-25（Asia/Shanghai）。

## 已复现的故障

- 设备：SHIELD Android TV，Android 11，arm64；安装版本 0.1.17。
- 通过 ADB 转发设备上的 Go 服务，分别请求豆包、咖啡的真实首页接口，两者均在约 10.02 秒返回 HTTP 502。
- JSON 中的实际错误为 `context deadline exceeded`，不是已确认的上游 HTTP 502。相同豆包请求在电脑 Go 服务约 0.85 秒成功。
- 保持原版本和协议，新启动的设备核心可以成功返回；重启应用后，设备界面恢复真实赛事数据。这个现象支持连接恢复存在缺陷，但不能据此排除上游和网络波动。
- 代码确认：首个请求可能耗尽共用截止时间，后续重试无剩余预算；取消等待的一个分支会绕过过期缓存兜底。界面又把所有非 2xx 响应简化成 HTTP 状态码。

## 最终处理

- 两个来源使用独立连接池。只对 GET，在慢请求开始 800ms 后，或第一次失败时，最多增加一次独立连接请求；完整有效响应先到者胜出，另一请求取消。
- 恢复连接成功后替换原连接池，后续请求复用可用连接。
- 保留系统 DNS、正常 TLS 证书验证及 HTTP 协议协商。对照中强制 HTTP/1.1、修改 TLS 算法、优先另一个 DNS 地址都没有稳定改善，未采用这些策略。
- API 请求总预算 6 秒；建连、TLS 握手和响应头分别有界。6 秒是失败上限，不是每次请求的固定等待。
- 赛事元数据新鲜期 30 秒，之后在现有 5 分钟兜底期内立即返回最近真实数据，并按缓存键合并后台刷新。房间和播放地址仍不使用该缓存。
- 直播卡片等待可选赛程补充最多 200ms；补充失败时不编造比分、队标或时间。
- 切页取消旧列表与分页请求；超时返回 HTTP 504 和来源对应文案；首次线路列表失败时，重试会重新请求列表。
- 失败日志只保留上游域名、连接阶段和耗时，不记录查询串、Cookie、响应体和视频地址。

## 设备真实接口抽样

最终连接策略的独立诊断核心，按首页、赛程、回放、全部直播顺序调用：

| 来源 | 首页 | 赛程 | 回放 | 全部直播 |
| --- | --- | --- | --- | --- |
| 豆包 | 200 / 1.829s | 200 / 3.621s | 200 / 1.944s | 200 / 0.211s |
| 咖啡 | 200 / 4.977s | 200 / 0.893s | 200 / 0.527s | 200 / 0.020s |

其中最后一次同类请求可能命中近期数据缓存。排查期间其他抽样仍出现咖啡 TLS 握手或响应头超时，以上 8 次成功不代表长期零故障。

这是运行在设备上的 Go 核心接口验证，不是升级后的正式 APK 验收。诊断二进制使用 Go 1.23.12、`CGO_ENABLED=0`；仅测试构建通过临时 overlay 指定设备当前网络报告的 DNS 服务器，模拟正式 CGO 核心的系统解析路径。该 overlay 和地址未进入产品源码。正式 APK 仍需由 GitHub CI 构建，并在同一设备复测。

## 回归检查

- Go race tests 与 Go 1.23.12 vet。
- 连接不返回响应头、只返回部分 JSON 响应体、恢复后的连接复用、败方取消、最多两次请求。
- 永久 HTTP 403 不重试、HTML 错误页不缓存。
- 最近数据立即返回、并发只触发一次刷新、后台刷新成功后替换数据。
- 可选补充接口不阻塞直播卡片、单来源超时返回来源对应的 504 文案。
- 浏览器故障注入：首次房间请求返回 504 时显示中文错误并聚焦重试；确认键触发第二次房间请求并重新显示加载状态。
- `node --check ui/app.js`、`git diff --check`。

当前技能结构校验通过；Go 测试位于 `core/internal/server/*_test.go`，列表分页和请求行为测试位于 `tests/`。

## 来源切换的首次失败恢复（0.1.18 之后）

用户反馈切换来源经常需要手动重试。代码确认有两个缺口：单来源列表失败后直接停在错误页；冷缓存请求随着页面取消而取消，快速切走再切回会丢弃正在获取的数据。电脑端的真实接口抽样和快速切换暂未复现用户的网络故障；设备安装版本确认是 0.1.18，但后续 ADB 命令超时，未取得该次故障日志。以下属于针对已确认代码缺口的修复，不声称排除了上游或设备网络问题。

- 列表元数据遇到临时网络错误、408 或 500/502/503/504 时，200ms 后自动补试一次。首次请求和补试共用最多 8 秒的界面等待预算，单次最多 6.2 秒；Go 的单次上游预算仍为 6 秒。两次失败后保留可聚焦的手动重试。
- 首屏、分页和全部来源均复用该策略，每个来源独立执行。分页补试期间保留已有卡片；单来源首屏仍显示加载状态，不将另一来源的卡片当成当前来源。
- 来源、分类、页码和游标在请求开始时固定。切页取消旧请求、补试定时器和回调，迟到结果不会覆盖新页面。
- 元数据冷加载和近期数据后台刷新共用按来源、完整路径和参数区分的请求。同键最多一个上游获取；页面取消只取消自己的等待，获取在最多 6 秒内完成并缓存，切回可直接复用。每来源最多 8 个后台获取，避免快速切页堆积，也不占用另一个来源的名额。房间及播放地址不使用这一机制。
- XHR 的 `readyState=4/status=0` 留给 `error`、`timeout`、`abort` 事件分类，避免请求超时或主动取消被误判为本地核心停止。

验证：Go race tests、vet、14 项 JavaScript 行为测试、JavaScript 语法检查和项目结构校验通过。浏览器在真实数据服务上注入首次列表 502 后，恰好自动请求第二次，恢复咖啡卡片且没有显示错误页；连续两次注入失败后停止自动请求并聚焦重试，确认键可恢复真实数据。单元测试覆盖取消后迟到回调、总等待预算、来源独立分页、元数据等待取消、缓存复用及后台请求上限。GitHub CI 继续执行 Android unit/lint/build。正式 APK 的盒子复测待设备连接恢复后进行。
